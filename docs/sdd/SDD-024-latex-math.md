## 1. Overview

Course sections generated by the Professor agent currently render math as raw
source text — dollar signs, backslashes and all — because:

1. `$...$` / `$$...$$` is not AsciiDoc syntax; Asciidoctor passes it through
   as plain text. AsciiDoc's native math mechanism is STEM (`:stem: latexmath`
   header, `stem:[...]` inline macros, `[stem]` delimited blocks).
2. No render path calls a typesetting library. Asciidoctor only wraps
   stem content in `\(...\)` / `\[...]` delimiters and expects the page to
   provide MathJax or KaTeX. None of the three paths (client viewer, HTML
   export, PDF export) provides one.

This design makes math render as typeset glyphs everywhere content appears,
without altering any stored content.

## 3. Decision record

### 3.1 Legacy `$...$` strategy: render-time normalization (not one-time migration)

**Decision:** render-time normalization applied in all three render paths.

**Justification:** A one-time migration would destructively rewrite
`lesson_content.content_adoc` rows that have already been verified by the
Reviewer agent and may have been read by students. If migration fails
mid-flight (partial update, crash, constraint violation) some rows end up in
an inconsistent state with no clear rollback path. Render-time normalization
is idempotent, can be rolled back by reverting the render code, and leaves
stored content as the source of truth forever. The brief designates
render-time as the safer default; this design adopts it.

The trade-off is that the normalization logic must exist in three places
(TypeScript client, Go HTML export path, Go PDF export path). Duplication is
justified per CLAUDE.md ("no speculative abstractions — implement exactly
what requirements specify"). Each path is self-contained; the algorithm is
simple enough that duplication carries low maintenance risk. A shared library
would require a cross-language abstraction (e.g. a subprocess or WebAssembly
module) that adds more complexity than it removes.

### 3.2 Normalization algorithm

The algorithm mirrors `renderMarkdown.ts`'s `extractMathTokens` /
`splitCodeRegions` approach. It must run on the raw AsciiDoc source **before**
Asciidoctor converts it, so dollar-span math is converted to stem macros that
Asciidoctor understands.

#### 3.2.1 Code-region exclusion

AsciiDoc code regions that must be excluded from dollar-sign extraction:

- Delimited listing blocks: `----` … `----` (4 or more hyphens)
- Delimited literal blocks: `....` … `....` (4 or more dots)
- Inline monospace: `` `...` ``
- Source blocks: `[source,...]\n----` … `----` (same fence, covered above)

The exclusion regex (TypeScript):

```
/(-{4,}|\.{4,}|`+)[^\n]*\n[\s\S]*?\n\1[ \t]*$|(`+)[\s\S]*?\2/gm
```

> **Rev 2 correction:** The original draft contained `\\.{4,}` which, in a
> JavaScript regex literal, means a literal backslash followed by any character
> (four or more times). It does NOT match `....` (four literal dots). The
> correct form is `\.{4,}`, which matches four or more literal dot characters.
> The incorrect form would have caused acceptance criterion 4 (`$HOME` inside
> a literal block must not typeset) to fail silently for `....`-fenced blocks.

Segments between matches are "non-code"; segments that are matches are
"code verbatim". Only non-code segments are scanned for dollar signs.

**Worked examples — regex match traces:**

The regex has two top-level alternatives separated by `|`:
- **Alt 1** (delimited block): `(-{4,}|\.{4,}|`+)[^\n]*\n[\s\S]*?\n\1[ \t]*$`
  — captures the opening fence in group 1, matches a newline, any content
  (lazy), then the same fence text (`\1` back-reference) at the end of a line.
- **Alt 2** (inline code span): `` (`+)[\s\S]*?\2 `` — captures one or more
  backticks in group 2, matches any content (lazy), then the same backtick
  count.

| Input fragment | Alt matched | Why |
|---|---|---|
| `----\nsome $x$ code\n----` | Alt 1, group 1 = `----` | `----` matches `-{4,}`; `\1` back-reference matches closing `----`; entire block is a "code verbatim" segment — `$x$` is never scanned |
| `....\nsome $x$ literal\n....` | Alt 1, group 1 = `....` | `....` matches `\.{4,}`; `\1` back-reference matches closing `....`; dollar sign excluded — note this would FAIL with the erroneous `\\.{4,}` which requires a leading backslash |
| `` `$HOME` `` | Alt 2, group 2 = `` ` `` | single-backtick inline code; dollar excluded |
| `prose $x$ text` | no match | neither alt matches; segment is "non-code"; `$x$` is scanned and converted to `stem:[x]` |
| `------\n...\n------` | Alt 1, group 1 = `------` | 6 hyphens; also matched by `-{4,}`; minimum fence length is 4 for both listing and literal |

Note that the minimum fence length for listing blocks (`----`) and literal
blocks (`....`) is 4 characters each. The `+` quantifier on the backtick
alternative allows any length >= 1.

#### 3.2.2 Dollar-to-stem conversion

Within each non-code segment, in order:

1. Replace `$$…$$` (display, possibly multi-line) with an AsciiDoc stem block:
   ```
   [stem]
   ++++
   <inner>
   ++++
   ```
2. Replace `$…$` (inline, single line, non-empty, no newline in inner) with
   `stem:[\<inner\>]`.

The `$$…$$` replacement is applied first to prevent the single-`$` pattern
from consuming one delimiter of a `$$` pair — the same ordering used in
`renderMarkdown.ts`.

#### 3.2.3 Residual heuristic limits

Dollar-sign detection is inherently ambiguous. Known false-positive triggers
that are NOT prevented by the code-region exclusion:

- Currency amounts in prose: "$10.99 per month" — the single-`$` regex
  requires a matching closing `$` on the same line, so "$10.99" alone does
  not match. A sentence like "costs $5 to $10" would match `$5 to $10` as
  inline math. This is a known limitation: well-formed math content avoids
  bare dollar amounts in prose. The brief accepts this residual risk.
- Shell variable references outside code blocks: `The path $HOME/bin` in a
  prose sentence. The closing `$` is absent so no match; `$VAR $OTHER` would
  match. Again, known limitation — prose containing shell variables should
  use inline code (`\`$VAR\``), which the code-region exclusion protects.

These limits are documented here and do not require mitigation in this sprint.
The `$HOME`-in-bash-snippet case that acceptance criterion 4 specifically calls
out is fully covered by the code-region exclusion (both `----`-fenced listing
blocks and `` ` ``-delimited inline code spans).

### 3.3 Going-forward STEM convention

Newly generated documents (post task 18.5 prompt change) use:

- `:stem: latexmath` in the document header.
- `stem:[E = mc^2]` for inline math.
- `[stem]\n++++\n…\n++++` for display/block math.

At render time, when the `:stem: latexmath` header is already present,
Asciidoctor wraps stem content in `\(...\)` / `\[...]` automatically. The
client-side KaTeX pass then typesets those delimiters.

For existing stored content that lacks the `:stem: latexmath` header,
**render-time header injection** is applied: the Go export functions and
the TypeScript `renderAsciidoc` function prepend `:stem: latexmath\n` to
the source before passing it to Asciidoctor. This is safe because the header
attribute is idempotent — setting it twice has no harmful effect.

## 4. Client pipeline (task 18.4)

File: `frontend/src/utils/renderAsciidoc.ts`

### 4.1 Pipeline order

```
raw AsciiDoc source (from API)
       |
       v
[1] normalizeDollarMath(source)
       — convert $…$ / $$…$$ outside code blocks to stem macros
       — prepend :stem: latexmath if not already present
       |
       v
[2] asciidoctor.convert(normalized, { safe: 'secure', standalone: false,
       attributes: { stem: 'latexmath', showtitle: true, icons: 'font',
                     'source-highlighter': '' } })
       — Asciidoctor wraps stem:[…] as <span class="stem">\(…\)</span>
       — Asciidoctor wraps [stem] blocks as <div class="stemblock">\[…\]</div>
       |
       v
[3] renderKatexInHtml(html)
       — scan the converted HTML for \(…\) and \[…\] delimiters
       — call katex.renderToString for each span, throwOnError: false,
         output: 'htmlAndMathml'
       |
       v
[4] sanitizeHtml(withMath)
       — DOMPurify with the extended SECTION_SANITIZER_CONFIG (see §5)
       — ALWAYS the final stage
       |
       v
safe HTML string → v-html
```

**Why this order:** Asciidoctor must run before KaTeX because it produces the
`\(...\)` and `\[...]` delimiters that KaTeX reads. DOMPurify must run last
so that any XSS payload introduced by malformed LaTeX (e.g. a KaTeX error
span containing attribute injections) is stripped before reaching the DOM.
`safe:'secure'` and the no-`include::` posture are not weakened; the stem
attribute does not require weakening them — Asciidoctor's stem processing is
pure text substitution with no file or shell access.

### 4.2 KaTeX render pass (step 3)

After Asciidoctor conversion, the HTML contains:

- Inline: `<span class="stem">\(…\)</span>` (Asciidoctor default output)
- Block: `<div class="stemblock"><div class="content">\[…\]</div></div>`

The `renderKatexInHtml` function:

1. Uses a regex to find `\(…\)` (inline) and `\[…\]` (display) spans in the
   HTML string.
2. Calls `katex.renderToString(inner, { displayMode, throwOnError: false,
   output: 'htmlAndMathml' })`.
3. Replaces the delimited span with the KaTeX output.

**Why regex-over-string (not DOM):** The simpler approach is chosen because
Asciidoctor's output is already structured — math content is wrapped in known
element classes — so a single-pass regex over the string is sufficient and
avoids adding any DOM parsing dependency to this utility function. The
function must also work in test environments where a full DOM may not be
available. This approach is a deliberate simplicity choice, not an SSR
requirement.

The `\(…\)` regex must not match across `</span>` or `</div>` boundaries;
it uses a non-greedy match that stops at the first `\)` or `\]` not preceded
by a backslash. This is safe for KaTeX's own output (which will not contain
nested `\(` sequences) and for content produced by the Professor agent.

### 4.3 KaTeX asset placement

KaTeX is imported in the same dynamic-import chunk as `@asciidoctor/core`.
The chunk is loaded only when a view that calls `renderAsciidoc` is mounted.
This keeps KaTeX JS, CSS, and fonts out of the main bundle.

Implementation: add `import katex from 'katex'` and
`import 'katex/dist/katex.min.css'` inside the dynamic-import callback in
`renderAsciidoc.ts` (or co-locate them in the same file so Vite bundles them
together). The font files referenced by `katex.min.css` are automatically
resolved as static assets by Vite's CSS asset pipeline and placed in
`dist/assets/`. No CDN references are emitted.

### 5.3 Style attribute: hook-based conditional allowance (BLOCKING 2 fix, rev 3 rewrite)

**Context:** The original draft §5.3 proposed removing `'style'` from
`FORBID_ATTR` on the grounds that the existing `afterSanitizeAttributes` hook
would compensate. This was incorrect. Reading `sanitizeHtml.ts:97-128`
confirms the hook only: strips `on*` event attributes, validates `img src`
schemes, and strips `javascript:` hrefs. It does not inspect `style` values
at all. DOMPurify 3.4.2 does not sanitize CSS at property level, so removing
`'style'` from `FORBID_ATTR` without adding explicit style inspection would
re-open the overlay attack surface covered by the existing probe test
(`sanitizeHtml.test.ts:11-23`, `position:fixed` full-screen div).

**Option (b) — keep `style` in `FORBID_ATTR` globally, post-process KaTeX
output — was evaluated and rejected:** KaTeX relies on inline styles for
core typesetting layout. Examining `katex/src/domTree.ts` reveals that KaTeX
emits the following inline style properties: `backgroundColor`,
`borderBottomWidth`, `borderColor`, `borderRightStyle`, `borderRightWidth`,
`borderTopWidth`, `borderStyle`, `borderWidth`, `bottom`, `color`, `height`,
`left`, `margin`, `marginLeft`, `marginRight`, `marginTop`, `minWidth`,
`paddingLeft`, `position`, `textShadow`, `top`, `width`, `verticalAlign`.
Stripping all `style` attributes after KaTeX renders would break
fraction baselines, accent positioning, and other structural layout. Moving
these to `data-*` attributes or CSS classes would require forking or
monkey-patching KaTeX internals — not feasible within sprint scope.

**Chosen approach: option (a) — extend `afterSanitizeAttributes` to apply a
conditional, property-scoped style allowlist.**

(Mechanism note: a hook-side "re-application" approach is impossible —
`FORBID_ATTR: ['style']` strips the attribute before `afterSanitizeAttributes`
fires, so the hook never sees it and cannot restore it. The mechanism is
therefore:)

1. Remove `'style'` from `FORBID_ATTR`.
2. Add `'style'` to `ALLOWED_ATTR` so DOMPurify passes it to the hook.
3. In `afterSanitizeAttributes`, inspect every element's `style` attribute.
   If the element is not a KaTeX/MathML element, strip `style` entirely.
   If the element IS a KaTeX/MathML element, validate the `style` value
   against the property-scoped allowlist described below and strip if it fails.

**KaTeX/MathML element identification:** An element qualifies as a KaTeX or
MathML math element if ANY of these conditions hold:

- The element's tag name is one of the MathML tags enumerated in §5.1
  (`math`, `mrow`, `mi`, `mn`, `mo`, `mfrac`, `msup`, `msub`, `msubsup`,
  `munder`, `mover`, `munderover`, `msqrt`, `mroot`, `mpadded`, `mspace`,
  `mtext`, `ms`, `mstyle`, `merror`, `mphantom`, `maction`, `mfenced`,
  `menclose`, `mtable`, `mtr`, `mtd`, `mlabeledtr`, `mglyph`, `malignmark`,
  `maligngroup`, `semantics`, `annotation`, `annotation-xml`).
- The element's `class` attribute contains at least one token matching
  `/^katex/` (KaTeX wraps its HTML output in elements with class names
  like `katex`, `katex-html`, `katex-mathml`, `katex-display`, etc.).
- The element has an ancestor (within the fragment being sanitized) whose
  `class` attribute contains a token matching `/^katex/` — i.e. the element
  is inside a KaTeX output subtree.

In practice, the check on the element itself (tag name in MathML set, OR
class starts with `katex`) is sufficient because all styled KaTeX spans carry
a `katex*` class. The ancestor walk is a belt-and-suspenders fallback; if
it has performance implications in practice, it can be dropped and the
element-level check alone relied upon.

**Property-scoped style validation (rev 3 replacement for the single-regex approach):**

The rev 2 allowlist used a single flat regex over the value side of each
declaration with a branch `| [a-zA-Z]+` annotated "named color or hex color".
That branch matched ANY purely-alphabetic string, meaning `position:fixed`,
`position:absolute`, `position:sticky`, `top:inherit`, `color:block`, and
countless other dangerous or nonsensical declarations all passed the
allowlist — directly undermining the stated overlay guarantee. The branch is
removed in rev 3.

**Handling of the `position` property (rev 4 — supersedes the rev-3 survey):**

The `CssStyle` type in `katex/src/domTree.ts` declares `position: string` as a
permitted field. The rev-3 survey of render functions (`buildCommon.ts`,
`accent.ts`, `array.ts`, `phantom.ts`, `smash.ts`, `sizing.ts`) missed
`op.ts`, which DOES assign `style.position = "relative"` inline for
non-limits single-symbol operators (`\int`, inline `\sum`, `\prod`, `\oint`)
— live-verified against KaTeX 0.17.0. `position` is therefore allowed with
the exact value `relative` only; all other values are rejected. See the
corrected note after the acceptance examples below.

**The allowed property set and its legal values, specified as (property, value-pattern) pairs:**

The hook splits each declaration on `;`, trims whitespace, skips empty tokens,
and for each `property:value` pair looks up the property in the table below.
If the property is not in the table, the declaration is rejected. If the
property is in the table, the value is tested against the listed pattern. If
any single declaration fails, the **entire `style` attribute is removed**.

```
GEOMETRY_VALUE  =  /^-?[0-9]+(\.[0-9]+)?(em|ex|px|rem|%)$/
                   OR the literal string "0" (unitless zero)
```

| Allowed property | Allowed value pattern | Rationale |
|---|---|---|
| `height` | GEOMETRY_VALUE | KaTeX uses em values for glyph sizing |
| `width` | GEOMETRY_VALUE | KaTeX uses em values for glyph sizing |
| `min-width` | GEOMETRY_VALUE | KaTeX uses em values for spacing |
| `top` | GEOMETRY_VALUE | KaTeX uses em values for vertical offset in vlist |
| `bottom` | GEOMETRY_VALUE | KaTeX uses em values for vertical offset |
| `left` | GEOMETRY_VALUE | KaTeX uses em values for horizontal offset (accents) |
| `vertical-align` | GEOMETRY_VALUE | KaTeX uses em values for baseline alignment |
| `margin` | GEOMETRY_VALUE | KaTeX uses em values |
| `margin-left` | GEOMETRY_VALUE | KaTeX uses em values |
| `margin-right` | GEOMETRY_VALUE | KaTeX uses em values |
| `margin-top` | GEOMETRY_VALUE | KaTeX uses em values |
| `padding-left` | GEOMETRY_VALUE | KaTeX uses em values |
| `border-bottom-width` | GEOMETRY_VALUE | KaTeX uses em values for rule thickness |
| `border-right-width` | GEOMETRY_VALUE | KaTeX uses em values |
| `border-top-width` | GEOMETRY_VALUE | KaTeX uses em values |
| `border-width` | GEOMETRY_VALUE | KaTeX uses em values |
| `color` | `/^(currentColor\|transparent\|#[0-9a-fA-F]{3,6})$/` OR KaTeX `\color` user-supplied hex/named value (see note) | KaTeX sets color for `\color` / `\textcolor` commands |
| `background-color` | `/^(currentColor\|transparent\|#[0-9a-fA-F]{3,6})$/` | KaTeX uses `currentColor` for stretchy mask images |
| `border-color` | `/^(currentColor\|transparent\|#[0-9a-fA-F]{3,6})$/` | KaTeX border color for rules |
| `text-shadow` | `/^none$/` | KaTeX emits `text-shadow:none` in error spans; only `none` is accepted |
| `border-right-style` | `/^(solid\|dashed\|dotted\|none)$/` | KaTeX uses solid/dashed for fraction rules |
| `border-style` | `/^(solid\|dashed\|dotted\|none)$/` | KaTeX uses solid for borders |

**Note on `color` user values:** The LaTeX `\color{red}` and `\textcolor{blue}{x}`
commands pass a user-supplied color string through `style.color`. KaTeX accepts CSS
color names (e.g. `red`, `blue`, `green`) and hex values. Rather than enumerate all
CSS named colors, the color-property allowlist accepts:
- The exact strings `currentColor` and `transparent`
- Any hex value matching `#[0-9a-fA-F]{3,6}`
- Any CSS named color: a string matching `/^[a-z]+$/` (lowercase alpha only)

This last sub-branch is PROPERTY-SCOPED: it applies ONLY to the three
color-bearing properties (`color`, `background-color`, `border-color`). It does
NOT appear in the value pattern for any geometry property. An attacker supplying
`position:fixed` cannot exploit this branch because `position` is not in the
allowed property set at all. An attacker supplying `height:fixed` cannot exploit
it because `height` only accepts GEOMETRY_VALUE (numeric with unit), not the
alphabetic sub-branch.

**Pseudocode for the hook validation function:**

```
GEOMETRY_VALUE_RE = /^-?[0-9]+(\.[0-9]+)?(em|ex|px|rem|%)$|^0$/

GEOMETRY_PROPS = new Set([
  'height', 'width', 'min-width', 'top', 'bottom', 'left',
  'vertical-align', 'margin', 'margin-left', 'margin-right', 'margin-top',
  'padding-left', 'border-bottom-width', 'border-right-width',
  'border-top-width', 'border-width',
])

COLOR_PROPS = new Set(['color', 'background-color', 'border-color'])

COLOR_VALUE_RE = /^(currentColor|transparent|#[0-9a-fA-F]{3,6}|[a-z]+)$/

BORDER_STYLE_PROPS = new Set(['border-right-style', 'border-style'])
BORDER_STYLE_VALUE_RE = /^(solid|dashed|dotted|none)$/

TEXT_SHADOW_VALUE_RE = /^none$/

function isDeclarationAllowed(prop, value):
  prop = prop.trim().toLowerCase()
  value = value.trim()
  if GEOMETRY_PROPS.has(prop):
    return GEOMETRY_VALUE_RE.test(value)
  if COLOR_PROPS.has(prop):
    return COLOR_VALUE_RE.test(value)
  if BORDER_STYLE_PROPS.has(prop):
    return BORDER_STYLE_VALUE_RE.test(value)
  if prop === 'text-shadow':
    return TEXT_SHADOW_VALUE_RE.test(value)
  // KaTeX emits position:relative inline for non-limits single-symbol
  // operators (\int, inline \sum, \prod, \oint) via op.ts when baseShift != 0.
  // 'relative' keeps the element in normal flow and cannot create an overlay;
  // every other position value is rejected (z-index is also not allowed, so
  // stacking abuse is blocked).
  if prop === 'position':
    return value === 'relative'
  return false  // unknown property — reject

function validateKatexStyle(styleAttrValue):
  declarations = styleAttrValue.split(';')
  for decl in declarations:
    decl = decl.trim()
    if decl === '': continue
    colonIdx = decl.indexOf(':')
    if colonIdx < 1: return false
    prop = decl.slice(0, colonIdx)
    value = decl.slice(colonIdx + 1)
    if not isDeclarationAllowed(prop, value): return false
  return true
```

A `style` attribute value is accepted if and only if `validateKatexStyle`
returns `true` for the full semicolon-delimited string. Any failing
declaration causes the entire `style` attribute to be removed from that
element.

**Note on the `position` property (corrected in rev 4):** rev 3 dropped
`position` entirely, claiming KaTeX never assigns `style.position` inline.
That claim was false — the rev-3 source survey missed `op.ts`. KaTeX's
`katex/src/functions/op.ts` (line ~138) sets `base.style.position =
"relative"` when `baseShift != 0` on single-symbol operators NOT in limits
mode, and `cssStyleToString` serializes every set key into the inline
`style=` attribute. Live execution against KaTeX 0.17.0 confirms:
`katex.renderToString('\\int f(x) dx')` emits
`style="margin-right:0.1945em;position:relative;top:-0.0006em;"` on the
op-symbol span; the same fires for inline `\sum`, `\prod`, and `\oint`.
Rejecting that declaration would strip the whole attribute — losing the
operator spacing (`margin-right`) and baseline shift (`top`), a visible
rendering regression on any expression containing those operators.

`position` therefore remains allowed but ONLY with the exact value
`relative`: `relative` keeps the element in normal document flow and cannot
create a fixed/viewport overlay, and `z-index` is not an allowed property,
so stacking abuse is blocked. `fixed`, `absolute`, `sticky`, and `inherit`
all fail the exact-match test, so both overlay probes still fail-strip.
(KaTeX's `.katex { position: relative }` stylesheet rule — PR #3859 — is
class-level and unaffected by attribute sanitization either way.)

**Non-KaTeX elements:** If the element does not qualify as a KaTeX/MathML
element (i.e. it has no `katex*` class and is not a MathML tag), the `style`
attribute is stripped unconditionally regardless of its value. This preserves
the existing behavior for all non-math content — Asciidoctor prose, tables,
code blocks — while allowing KaTeX math layout.

**Both probes must fail-strip; legitimate sizing must pass:**

The design guarantees that both the plain-div overlay probe AND the
katex-classed-span overlay probe are neutralized:

- **Plain-div overlay probe** (`<div style="position:fixed;top:0;left:0;
  width:100%;height:100%;z-index:9999">`): the div carries no `katex*` class
  and is not a MathML tag, so the hook strips its `style` attribute
  unconditionally before the allowlist is even consulted.
- **KaTeX-classed-span overlay probe** (`<span class="katex"
  style="position:fixed;top:0;left:0;width:100%;height:100%;z-index:9999">`):
  the span qualifies as a KaTeX element (class starts with `katex`), so the
  allowlist IS consulted — but `position` only admits the exact value
  `relative`, so `fixed` fails, `validateKatexStyle` returns `false` on the
  first declaration, and the entire `style` attribute is stripped. The span

- **Legitimate sizing pass-probe** (`<span class="katex-html"
  style="height:0.694em;vertical-align:-0.5em;margin-right:0.1667em">`):
  all three declarations pass their respective GEOMETRY_VALUE_RE tests, so

## 6. HTML export — self-contained, no CDN (task 18.3)

**Decision:** server-side pre-rendering of math into the exported HTML.

**Justification:** The alternative is inlining KaTeX JS/CSS/fonts into the
HTML file so the browser can typeset on load. This alternative has two
problems:

1. KaTeX JS + CSS + fonts total ~500 KB–1 MB. A self-contained HTML export
   embedding all of that is unwieldy as a student download.
2. The server already runs the asciidoctor subprocess; adding a second
   subprocess (a Node.js script that calls KaTeX) or a Go KaTeX port is
   significant complexity.

Pre-rendering math server-side using a small Go-callable Ruby script (or
a compiled KaTeX approach) was also considered, but all options require
running JavaScript server-side.

**Chosen approach:** The export endpoint injects `:stem: latexmath`, runs
`asciidoctor` with `--attribute stem=latexmath`, and appends inline KaTeX
CSS (the minified stylesheet) and a `<script>` tag that calls
`renderMathInElement` from KaTeX's auto-render extension. The JS and CSS
are read from the Go binary's embedded filesystem (using Go's `embed` package)
and written as `<style>` and `<script>` tags into the exported HTML, so no
external network call is ever needed.

Concretely:

1. `asciidoctor` is called with `-a stem=latexmath -a` (passing the stem
   attribute) to ensure Asciidoctor wraps STEM content in `\(...\)` /
   `\[...]`. Dollar-span content has already been converted to STEM macros
   by the Go normalization function before the temp file is written.
2. The exported HTML output has KaTeX CSS (`katex.min.css`) injected as an
   inline `<style>` block and KaTeX JS (`katex.min.js`) plus the
   auto-render extension (`auto-render.min.js`) injected as inline
   `<script>` blocks in `<head>` / at end of `<body>`.
3. KaTeX and auto-render files are embedded in the Go server binary via
   `//go:embed` directives pointing at assets in `internal/content/assets/`.
   Those files are copied from the frontend build's `node_modules/katex/dist/`
   at Docker build time (the Dockerfile copies them before the Node build
   artifacts are discarded).
4. Font files referenced by `katex.min.css` are base64-inlined using a small
   Go function that rewrites `url(fonts/...)` references in the CSS to
   `url(data:font/woff2;base64,...)` before injection. This ensures the
   exported HTML truly has no external dependencies.

**KaTeX font completeness (rev 2 addition):** `katex.min.css` contains
`@font-face` rules referencing fonts in three formats: woff2 (primary),
woff (fallback for older browsers), and ttf (legacy fallback). All three
format variants must be embedded in `internal/content/assets/fonts/`. The
base64-inlining function must rewrite ALL `url(fonts/...)` references in the
CSS — woff2 first, then woff, then ttf — so the exported HTML renders
correctly in both modern and older browsers. Embedding only woff2 will cause
rendering failures in environments that do not support woff2 (certain
WebKit-based PDF renderers). The implementation checklist in §13 reflects
this requirement.

This is more complex than inlining the full bundle at build time, but it
produces smaller exported files and reuses infrastructure already present
(the Go embed pattern, the existing subprocess invocation).

**Acceptance criterion 3 coverage:** the exported HTML opens in a browser
with networking disabled and math typesets correctly, because all JS, CSS,
and font data are inline in the file.

## 11. Alternatives considered

### 11.1 One-time content migration (rejected)

Run a SQL `UPDATE lesson_content SET content_adoc = normalize(content_adoc)`
to convert all stored `$…$` spans to `stem:[…]` in one shot, then remove the
normalization layer. Rejected because: destructive rewrite of verified content;
no safe rollback path; migration failure leaves database in mixed state.
See §3.1 for full justification.

### 11.2 MathJax instead of KaTeX (rejected, out of scope)

MathJax is larger, asynchronous, and not already present. The brief
explicitly prohibits adding a second typesetter. KaTeX is synchronous and
already installed.

### 11.3 Inlining full KaTeX bundle in HTML export (rejected)

~1 MB added to every HTML export file. Server-side pre-rendering (chosen
approach, §6) produces smaller files and is more consistent with the
in-app rendering quality.

### 11.4 Server-side pre-rendering via Node.js subprocess (rejected)

Would require Node.js in the backend Docker image, adding substantial image
weight, a second runtime, and process management complexity. The chosen
inline-JS approach (§6) keeps the server image Ruby-only.

### 11.5 Weakening `safe:'secure'` to enable stem (rejected, binding)

The brief explicitly forbids weakening `safe:'secure'`. Stem rendering does
not require it — Asciidoctor processes stem content as text substitution at
the document model level, not via file inclusion or shell execution.

### 11.6 Style allowlist option (b): keep `FORBID_ATTR: ['style']` globally, post-process KaTeX output (rejected)

Evaluated in §5.3. KaTeX uses a wide set of CSS properties as inline styles
that are structurally necessary for math layout. Stripping all `style`
attributes post-render breaks fraction baselines and accent placement. Moving
these to `data-*` attributes or CSS classes would require forking KaTeX
internals. Infeasible within sprint scope.

### 11.7 Denylist-based style sanitization (rejected in favour of allowlist)

A denylist approach (strip any value containing `position`, `fixed`,
`absolute`, `z-index`, `url(`, `expression(`) was considered for the style
allowlist logic in §5.3. Rejected because CSS property names and values have
too large an attack surface to enumerate safely; new CSS properties or vendor
extensions not on the list could be exploited. An allowlist of the exact
properties KaTeX emits (verified against `katex/src/domTree.ts` and the
render functions) is smaller and provably closed.

### 11.8 Single-regex value allowlist (rev 2 approach, rejected in rev 3)

The rev 2 allowlist used a single regex across all property value sides,
with a branch `| [a-zA-Z]+` annotated "named color or hex color". This branch
matched ANY purely-alphabetic string, causing `position:fixed`,
`position:absolute`, `position:sticky`, and `top:inherit` to pass the
allowlist — directly contradicting the stated overlay guarantee and
re-opening the phishing attack via a katex-classed span. Replaced in rev 3
with per-(property, value) pair validation where the alphabetic sub-branch
is ONLY reachable on the three color-bearing properties (`color`,
`background-color`, `border-color`) and is unreachable from any geometry
or positioning property. Rev 4 corrected one factual error in the rev-3
property survey: KaTeX DOES emit `position:relative` inline via `op.ts`
(non-limits single-symbol operators such as `\int`), so `position` is
allowed with the exact value `relative` only — see the corrected note in
§5.3.
