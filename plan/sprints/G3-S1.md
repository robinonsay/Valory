# G3-S1 — Run lifecycle & bounded dispatch (Sprint 31)

> Level 2, goal G3. Owned by `software-lead`. The **active frontier** of G3. Stops the
> re-trigger storm and makes generation dispatch idempotent and bounded. Backend-focused; no
> frontend. Backward compatible with existing flat + tree courses.

## Problem this sprint fixes

`pollAndGenerate` re-derives eligible work every 30s from course status + run status alone. A
failed run leaves the course in `syllabus_approved`, so it is immediately re-eligible → the poller
re-triggers it every cycle. Over a demo session this produced **925 failed `content_generation`
runs in 10h** (~2/min). There is no retry budget, no backoff, no terminal failure state, and no
explicit in-flight guard on the flat path (the tree path bolted on a `sync.Map`; the flat path
relies on the incidental `agent_runs.status` default `'running'`). This sprint introduces an
explicit, durable **run lifecycle** and **bounded, idempotent dispatch**, unified across flat and
tree.

## Lead decisions (binding for this sprint)

| # | Decision |
|---|---|
| **D17** | **Retry policy lives in the eligibility query + a durable per-course attempt/backoff record**, not in the goroutine. A course is eligible only if it has no running/completed run AND no failed run inside the backoff window AND has not exhausted max-attempts. This keeps the poller stateless and the policy declarative. |
| **D18** | **Exhausted retries → terminal course state `generation_failed`** (new status), which the poller never selects. Recovery is an explicit action (student/admin re-trigger), satisfying REQ-AGENT-003 ("failed does not *permanently* block" → bounded auto-retry, then a manual gate; not infinite auto-retry). |
| **D19** | **Idempotent claim, unified flat+tree.** Dispatch claims a run via an atomic transition (or a single in-flight registry used by *both* paths) so a course can never have two concurrent runs. Remove the flat/tree divergence (one guard, both paths). |
| **D20** | **No schema for cost yet.** Cost pre-flight + Brave accounting are **G3-S2**. S1 only adds the lifecycle scaffolding (attempt count, backoff timestamp, terminal state). Keep the migration additive and idempotent (next number after 023 = **024**). |
| **D21** | **Retry budget is course-dispatch-level** (resolves T1's OQ-2). The backoff + max-attempts → terminal `generation_failed` budget counts failed `content_generation`/`tree_layer_generation` runs **per course since the course last reached a terminal SUCCESS** (flat → `active`; tree → tree-generation-complete) — NOT individual sub-layer retries within one tree run. The counter resets ONLY on terminal success, never on an intermediate layer `completed` (resetting per-layer would let a course failing layer 5 forever escape the bound = a slower storm). This is the level the 925-run storm occurred at. |
| **D22** | **A terminal `generation_failed` course must not count against the single-active-course limit.** Migration 024 widens `courses_single_active_idx` to `WHERE status NOT IN ('archived','completed','generation_failed')` so a student whose generation terminally failed can start a new course (they can also delete the failed one or use the explicit recovery action — REQ-AGENT-069). Found by the T3 gate as a UX gap; folded into 024. |
| **D23** | **Edit migration 024 in place to add the new `pipeline_event_type` enum values.** T4's runner emits 4 new pipeline events (`generation_claimed`, `token_cap_preflight_failed`, `generation_failed_with_retry`, `generation_terminal`); the `pipeline_events.event_type` enum must carry them or the (error-discarded) inserts silently fail in prod. Migration 024 is **unreleased** (the running prod image predates G3; the prod DB is at migration 023), so amending 024's pre-`BEGIN` enum-additions section is correct rather than spawning a new migration. `ALTER TYPE ... ADD VALUE IF NOT EXISTS`, keep idempotent. Found by the T4 re-gate (Systems). |
| **D24** | **The tree-path terminal-success reset (`ResetAttemptCount`) fires when `settleLayer` settles the final (content) layer** — not in `dispatchTreeCourse` after the seed (which only generates the root/section_goal layer → premature reset that un-bounds the storm; the T4 re-gate SQE blocker). After the content layer's generation settles, no further generation runs are dispatched for the course, so that is the true terminal of the *generation* storm. Wire it in `layered_runner.go settleLayer` gated on `layer == NodeTypeContent` (the `approvedOrAwaiting > 0` branch) via `lr.agentRepo.ResetAttemptCount` — deterministic, poller-driven, fires exactly once (the course leaves the `generating` pool on settle). Do NOT depend on the `node_handler` `ErrTreeComplete`/expand path (a UI action that may never fire). This resolves the design's abstract "tree-generation-complete event" against the actual G2-S3 code, which has no explicit tree-terminal status transition. |

## Requirements in scope

`REQ-AGENT-003` (retry not permanently blocked — re-interpreted as bounded auto-retry),
`REQ-AGENT-014` (timeout), `REQ-SYS-074` (cost safety — partial: fail-fast hook here, full gate in
S2). New `REQ-AGENT-061+` authored in T2.

## Definition of done

A persistently-failing course produces a bounded number of runs and reaches `generation_failed`
(no storm); dispatch is provably single-run under a race; flat and tree share one guard; a
token-capped run fails before doing per-section paid work; existing happy-path generation still
completes. All under the acceptance facet; RLS/role context preserved. Closes when T1–T5 pass.

**Open question logged for G3-S3 (resilience), NOT closed here:** the `pollLayeredGeneration`
layer-loop is not bounded by the dispatch-level attempt counter — a persistently-failing tree
*layer* leaves the course in `'generating'` and `handleFailedRun` is not called on that path, so a
failed layer can re-create a `tree_layer_generation` run every tick (DB-row accrual; paid work is
limited only by failed nodes not being retried). G3-S1 bounds the *dispatch/eligibility* storm (the
925-run incident); the per-layer loop bound is a distinct G3-S3 concern. Also: test-role superuser
masks the FORCE-RLS courses server-policy (pre-existing; G3-S3/G4).
