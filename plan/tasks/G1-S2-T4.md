# G1-S2-T4 — Frontend: admin course-material browser

> Level 4 task contract. Owned by `software-lead`.

- **Verifier (acceptance gate):** SQE + Systems Engineer
- **Depends on:** G1-S2-T2
- **Artifact path:** `frontend/src/views/admin/` (new course-detail view) + router + API

## Design (how — the mandate)

Add an admin **course-detail / material browser** reachable from Course Oversight. From the
oversight list (`CourseOversightView.vue`, which after G1-S1 shows the student **name**), an
admin opens a course and browses, **read-only**:

- the syllabus,
- section list + lesson content (rendered),
- homework + rubric,
- submission status and grades.

Consume `GET /admin/courses/{id}/overview` (from G1-S2-T2). No edit/regenerate controls — this
is read-only oversight (PM decision #2); the interactive authoring flow is G2. Follow the
existing admin view conventions (Composition API, `<script setup>`, TypeScript). Add a
component test. Reuse existing content-rendering components where they exist (the student
content viewer) rather than duplicating AsciiDoc rendering.

## Requirements (what-for)

- **REQ-FEADMIN-707** (authored in G1-S2-T1). Components annotated to trace the requirement
  per the project's frontend tracing convention.

## Acceptance (done-criteria)

- [ ] An admin can navigate Oversight → a course → browse syllabus, sections + content,
      homework + rubric, submissions, grades — all read-only.
- [ ] No mutation controls present (no edit/regenerate/delete).
- [ ] Types match the `/admin/courses/{id}/overview` response shape.
- [ ] Component test covers the happy path and the loading/error states.
- [ ] Frontend builds and typechecks clean.
