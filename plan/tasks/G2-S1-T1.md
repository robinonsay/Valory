# G2-S1-T1 — TDD: knowledge-tree DAG data model

> Level 4 task contract. Owned by `software-lead`. **No production code** — design only.

- **Worker:** design-author
- **Verifier (acceptance gate):** Senior SQE
- **Depends on:** none (independent design facet; parallel with T2, T3)
- **Artifact path:** `docs/design/knowledge-tree-data-model.md`; summary under
  `plan/artifacts/G2-S1-T1/`

## Design (how — the mandate)

Produce a Technical Design Document for the knowledge-tree **DAG data model** that re-frames a
course as a tree grown layer by layer:

```
root (course intent) → syllabus → per-section goals → concepts → content
```

Specify a `course_nodes` table (at minimum): `id`, `course_id`, `parent_id` (self-FK, nullable
for root), `node_type` ∈ {`root`, `syllabus`, `section_goal`, `concept`, `content`}, `ordering`,
`status` (e.g. `pending`/`generating`/`awaiting_review`/`approved`/`rejected`), `payload`
(JSONB for node content), timestamps. Justify DAG vs. strict tree (the user described a
"DAG tree"; decide and document whether nodes may have multiple parents and why).

**Hard constraints:**
- **Coexistence, not migration.** Legacy flat `syllabi` / `homework` / `lesson_content`
  ([003_course.sql](../../migrations/003_course.sql), [004_agent.sql](../../migrations/004_agent.sql))
  and in-flight flat courses must keep working unchanged. No piecemeal migration of legacy data
  (CLAUDE.md). Document how a course is marked tree-backed vs. flat and how each renders.
- **RLS from day one.** `course_nodes` must carry policies mirroring `courses`: student-owns
  (via `app.current_user_id`), admin-all (`app.current_role='admin'`), server-write
  (`app.current_role='server'`), with the `NULLIF` guard (memory
  `force-rls-superuser-test-masking`). Specify them in the TDD; the migration is built in G2-S2.
- Indexes for the two hot access patterns: fetch a node's children, and fetch a whole layer
  (`node_type`) for a course.
