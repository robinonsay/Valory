# G2-S2-T4 — DB integration tests: student `course_nodes` tree CRUD + RLS

> Level 4 task contract. Owned by `software-lead`.

- **Worker:** test-author
- **Verifier (acceptance gate):** SQE
- **Depends on:** G2-S2-T2 (the student tree repository)
- **Artifact path:** `internal/agent/tree_repository_integration_test.go` (new); summary under

## Design (how — the mandate)

Real-Postgres integration tests for the student tree repository (G2-S2-T2). **No mocks**
(CLAUDE.md). Follow the existing integration-test idiom exactly:
`//go:build integration`, `VALORY_TEST_DATABASE_URL`, `dbpkg.IntegrationPool(t)`, `-p 1` (memory
`valory-db-test-drift`). Use the migration `022` schema (applied by the test harness’s migration
step).

### Required coverage

1. **CRUD round-trip** — create root → syllabus → section_goal → concept → content chain;
   `GetNode`, `ListNodesByCourse` (with `node_type` filter), `ListChildren` (ordering); JSONB
   payload survives round-trip.
2. **Atomic status transition** — `TransitionNodeStatus` returns true on the matching `from`
   state and false on a stale `from` (proves the test-and-set guard; no lost-update).
3. **Layer aggregate** — seed a layer with mixed approved/failed/pending and assert
   `LayerAggregate` counts.
4. **node_chats** — append user+assistant turns, list in `created_at` order.
5. **RLS isolation — the critical facet (memory `force-rls-superuser-test-masking`):** every
   ownership assertion runs **under `SET ROLE valory_app`** (not the superuser test role):
   - student A can read/affect only their own course's nodes;
   - student B canNOT read student A's nodes (cross-student denial → 0 rows);
   - admin role (`app.current_role='admin'`) can read any student's nodes;
   - server role can insert/update;
   - student cannot INSERT/UPDATE `course_nodes` directly (policy denies).
   Use a `SET ROLE valory_app` + `SET app.current_user_id/app.current_role` helper (mirror the
   `verifyValoryAppGrants` pattern from `internal/user/integration_test.go`). A test that
   asserts isolation while connected as superuser is INVALID — it masks RLS bugs.

### Annotations

Each test carries `// @{"verifies": ["REQ-AGENT-0nn", ...]}` (colon form) naming the
requirement(s) it exercises — bind to the same IDs the T2 repo functions claim, plus
`REQ-SYS-075`.

## Acceptance (done-criteria)

- [ ] Tests build under `-tags integration` and run green against a real Postgres with
      `VALORY_TEST_DATABASE_URL` set, `-p 1`.
- [ ] Cross-student denial and admin-all are both asserted **under `SET ROLE valory_app`**.
- [ ] Direct student write to `course_nodes` is shown to be denied by RLS.
- [ ] No mocks; no superuser-masked assertions.
- [ ] Every test annotated with the requirement IDs it verifies.
