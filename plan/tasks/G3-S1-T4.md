## Mandate (implement per the design)
1. **Unified idempotent dispatch (D19).** `pollAndGenerate`: read `generation_max_attempts` +
   `generation_backoff_seconds` from config (defaults 5 / 600), pass `maxAttempts` to
   `ListUntriggeredApprovals`. Guard dispatch with a process-level in-flight registry for the FLAT
   path mirroring `inFlightLayered` (call it `inFlightFlat`) — one mechanism shape for both paths —
   AND tolerate `ErrRunAlreadyClaimed` from `CreateRun` (the DB partial-unique-index is the
   cross-process guard). Exactly one concurrent run per course must hold under a forced race.
2. **Tolerate the claim at all CreateRun sites.** `pollLayeredGeneration` (runner.go ~470) and
   `seedTreeAndGenerateRoot` (layered_runner.go ~915) must treat `ErrRunAlreadyClaimed` as a
   benign skip (not an error log), per the design's defence-in-depth note.
3. **Retain `RunContentGeneration` intact (C2).** Keep its timeout context (REQ-AGENT-014),
   `handleTimeout`/`handleAPIFailure` classification, and `UPDATE courses SET status='active'`.
   Wrap it with the lifecycle hooks; do NOT inline-replace it with `generateAllSections`.
4. **Cost fail-fast (§9.2, REQ-AGENT-068).** Add `tokenCapPreFlight` at the dispatch goroutine,
   BEFORE any section/Brave/Claude work, so an over-cap run fails immediately (records a failed run
   → backoff applies) and makes ZERO per-section Brave calls. (Full cost gate is G3-S2.)
5. **Retry/terminal flow (§6.2, D18/D21).** On a run FAILING: the caller sets the run status failed
   (per the design, `handleFailedRun` does NOT itself call `SetRunStatus` — avoid a double UPDATE),
   then `IncrementAttemptCount` (sets `next_eligible_at` = now + backoff), then if
   `ConsecutiveFailures(course) >= maxAttempts` call `SetCourseTerminal('generation_failed')` and
   emit/notify the terminal event. On a run SUCCEEDING (course reaches terminal success — flat
   `active`; tree complete): call `ResetAttemptCount` (D21 — reset ONLY on terminal success, never
   per layer). Emit the lifecycle events the design names.
6. **Startup recovery ordering (§8.3, M5).** Ensure config loads BEFORE the stale-run/backoff bulk
   update (which needs the backoff config). `cmd/server/main.go` currently runs recovery (~line 106)
   before config load (~line 114) — move recovery after config load (or split it) so ordering is:
   migrations → load config → mark stale `running` runs failed → apply attempt-count/terminal. Guard
   the bulk update to `status='syllabus_approved'` so it cannot touch active/terminal courses.
7. **Document the chosen reconciliation** (design left option a/b): in a code comment, state how
   `RunContentGeneration`'s internal `SetRunStatus` calls reconcile with the outer lifecycle hooks
   (no double `completed_at` stamp).

## Constraints
- Idiomatic Go, parameterized queries, `context.Context` preserved; `@{"req": [...]}` annotations
  citing REQ-AGENT-062/064/065/066/067/068/069 / REQ-SYS-074 as applicable.
- RLS/role: poller has no request context → server pool; `courses` writes via the server role
  (T3's repo methods already do this); never a bare-pool write to a FORCE-RLS table.
- Scope: NO cost accounting/Brave ledger (G3-S2), NO concurrency/resumability (G3-S3) beyond the
  named hooks. Do NOT change `repository.go` logic (T3) except trivially if a signature needs it.
- `export PATH=/usr/local/go/bin:$PATH`; `go build ./...` + `go vet ./...` clean. Live integration
  is T5 (the Docker stack is DOWN — do not start the full app stack). A throwaway test PG for a
  quick sanity build is optional.

## Acceptance (done-criteria)
